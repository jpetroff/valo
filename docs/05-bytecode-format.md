# Chapter 5 — The Bytecode Format

Before looking at how code is generated (chapter 6) and executed (chapter 7),
we fix the language both sides speak: the instruction set and the containers
that hold compiled code. All of it lives in the VM crate, because the VM must
be able to run bytecode without the compiler.

## 5.1 Theory: virtual machines and instruction sets

An interpreter can execute the syntax tree directly ("tree-walking"), or
first compile it to a linear sequence of simple instructions — **bytecode** —
for a **virtual machine**. Bytecode is faster to execute (no pointer chasing
through tree nodes, compact in memory), can be saved to a file and loaded
later, and makes the runtime independent of the parser.

Two VM designs dominate:

| | Stack machine | Register machine |
|---|---|---|
| operands | implicit, on an operand stack | named slots ("registers") in the instruction |
| `a = b + c` | `PUSH b; PUSH c; ADD; STORE a` (4 instr.) | `ADD a b c` (1 instr.) |
| examples | JVM, CPython, WebAssembly, Lua ≤ 4 | Lua 5, Dalvik (Android), Erlang BEAM |
| pros | tiny instructions, trivial code generation | fewer instructions and copies → faster |

Lua 5.0 switched from stack to registers and reported a substantial speedup
(Ierusalimschy et al., 2005). valo follows Lua 5: **registers are slots in the
current function's window of the value stack**, numbered from 0 (`R0`, `R1`, …).

## 5.2 Instruction encoding

File: [`vm/src/opcode.rs`](../vm/src/opcode.rs)

Every instruction is one 32-bit word, `struct Instr(pub u32)`. The low byte
is the **opcode**; the remaining 24 bits hold operands in one of four
**formats**:

```text
 bit 31            24 23            16 15             8 7              0
     +---------------+---------------+---------------+---------------+
iABC |       C       |       B       |       A       |    opcode     |
iABx |           Bx (u16)            |       A       |    opcode     |
iAsBx|           sBx (i16)           |       A       |    opcode     |
isJ  |                 sJ (i24, two's complement)    |    opcode     |
     +---------------+---------------+---------------+---------------+
```

- `A`, `B`, `C`: 8-bit register numbers → at most 255 registers per function.
- `Bx`: 16-bit unsigned — constant index (`LOADK`), global index (`GETGLOBAL`, `SETGLOBAL`).
- `sBx`: 16-bit signed — small integer immediates (`LOADI`, −32768…32767).
- `sJ`: 24-bit signed — jump offsets (`JMP`), relative to the next instruction.

Lua 5.4 packs fields more tightly (7-bit opcode, 17-bit Bx); valo uses
byte-aligned fields because decoding is just shifts and the format is easier
to read in a hex dump (plan decision D2).

Encoding and decoding are plain bit operations:

```rust
Instr::abc(OpCode::ADD, 0, 0, 1)          // = 4 | 0<<8 | 0<<16 | 1<<24
instr.a()   // (self.0 >> 8) as u8
instr.sbx() // (self.0 >> 16) as u16 as i16      — reinterpret the 16 bits as signed
instr.sj_offset() // (self.0 as i32) >> 8        — arithmetic shift sign-extends 24 → 32 bits
```

The property tests at the bottom of `opcode.rs` check that encode → decode
returns exactly the inputs for random values, including the extremes.

## 5.3 The instruction set

`OpCode` is generated by the `opcodes! { … }` macro from one list of
`NAME = number, FORMAT;` lines (chapter 1, *Macros*), so the enum, the
mnemonic table (`OpCode::name`) and the format table (`OpCode::format`)
cannot disagree. **All 41 opcodes of the MVP plan are declared now**, so their
numbers never change; the VM implements them milestone by milestone.

Implemented so far (M1–M3):

| Opcode | Format | Semantics |
|--------|--------|-----------|
| `LOADUNIT A` | A | `R[A] = ()` |
| `RETURN A` | A | return `R[A]` from the function |
| `LOADI A sBx` | AsBx | `R[A] = sBx` (small integer immediate) |
| `LOADK A Bx` | ABx | `R[A] = K[Bx]` (constant pool) |
| `LOADBOOL A B` | AB | `R[A] = (B != 0)` |
| `ADD/SUB/MUL/DIV/IDIV/MOD/POW A B C` | ABC | `R[A] = R[B] op R[C]` (`DIV` = true division, always float) |
| `NEG A B` | AB | `R[A] = -R[B]` |
| `NOT A B` | AB | `R[A] = not R[B]` (bool only) |
| `EQ/NE/LT/LE A B C` | ABC | `R[A] = R[B] cmp R[C]`; `>`/`>=` are `LT`/`LE` with B and C swapped |
| `MOVE A B` | AB | `R[A] = R[B]` |
| `GETGLOBAL A Bx` | ABx | `R[A] = G[Bx]` (R0302 if not set yet) |
| `SETGLOBAL A Bx` | ABx | `G[Bx] = R[A]` |
| `TEST A B` | AB | `R[A]` must be a bool (R0203); if `R[A] != B`, skip the next instruction |
| `JMP sJ` | sJ | `pc += sJ` |
| `ASSERT A B` | AB | `R[A]` must be true, else R0701; with B=1, `R[A+1]`/`R[A+2]` hold the two sides for the message |
| `ECHO A` | A | print `R[A]` (debug aid for `--echo`) |

`TEST` + `JMP` is Lua's branch pair: `TEST` decides whether the following
`JMP` runs (it runs when `R[A] == B`).

Declared for later: `CALL`,
`CLOSURE` (M4); `TAILCALL` (M5); `GETUPVAL`, `GETSELF` (M6); `CONCAT`,
`LOADNONE`, `TRY` (M7); `NEWLIST`, `INDEX` (M8); `NEWTUPLE`, `NEWDICT`,
`GETFIELD` (M8b); `LOADMISSING`, `JMPIFSET` (M4b); `CHECKTYPE` (M10). The
full table with semantics is in `.memory/plan-mvp.md` §2.2.

Note the "three-address" shape `ADD A B C`: destination and both sources are
named, and they may coincide (`ADD 0 0 1` = `R0 = R0 + R1`).

## 5.4 Prototypes and programs

File: [`vm/src/chunk.rs`](../vm/src/chunk.rs)

A **prototype** is one compiled function (Lua's `Proto`). It is a template:
at runtime (M4+) a *closure* pairs a prototype with captured values.

```rust
pub struct Proto {
    pub name: Rc<str>,          // "<main>", a function name, "<lambda@3:9>"
    pub arity: u8,              // number of parameters (0 for <main>)
    pub num_regs: u8,           // registers the frame needs (computed by codegen)
    pub code: Vec<Instr>,       // the instructions
    pub consts: Vec<Const>,     // the constant pool
    pub spans: Vec<SrcSpan>,    // spans[pc] = source of code[pc]   (chapter 2)
    pub def_span: SrcSpan,      // where the function is defined
    pub protos: Vec<Rc<Proto>>, // nested functions (CLOSURE operand)
    pub locals: Vec<LocalInfo>, // debug info: register ↔ variable name, per pc range (chapter 13)
    pub upvals: Vec<UpvalDesc>, // what a closure of this fn captures (M6, chapter 6)
}
pub struct UpvalDesc { pub src: UpvalSrc, pub name: Rc<str> }
pub enum UpvalSrc { Reg(u8), Upval(u8), Current }   // where CLOSURE takes each value

pub enum Const { Int(i64), Float(f64) }     // M7 adds Str

pub struct Program {
    pub main: Rc<Proto>,        // top-level code
    pub globals: Vec<GlobalDesc>, // one per top-level `let` (name, for messages)
    pub source_name: Rc<str>,   // file name for messages
    pub line_starts: Vec<u32>,  // line index (chapter 2)
}
```

### The constant pool

Values that do not fit in an instruction are stored once in the prototype's
`consts` table and loaded by index: any integer outside −32768…32767
(`70000` becomes `LOADK 1 0` with `consts[0] = Int(70000)`) and every float.
Each distinct value is stored once (deduplication in codegen, chapter 6;
floats are compared by bit pattern, so `0.0` and `-0.0` stay distinct).
Strings (M7) will use the same mechanism.

### ProtoBuilder

`ProtoBuilder` assembles prototypes by hand, for VM tests that must not depend
on the parser (and for testing opcodes before the parser supports them):

```rust
let program = ProtoBuilder::new("<main>", 2)
    .konst(Const::Int(70000))
    .op(Instr::asbx(OpCode::LOADI, 0, 2))
    .op(Instr::abx(OpCode::LOADK, 1, 0))
    .op(Instr::abc(OpCode::ADD, 0, 0, 1))
    .op(Instr::abc(OpCode::RETURN, 0, 0, 0))
    .program();
```

## 5.5 Reading a disassembly

File: [`vm/src/disasm.rs`](../vm/src/disasm.rs) — `disassemble(&Program) -> String`.

```text
function <main> arity=0 regs=3 consts=1   ; t.vl:1:1
  0000  [1:2]   LOADI     0 1
  0001  [1:6]   LOADK     1 0      ; 70000
  0002  [1:1]   ADD       0 0 1
  0003  [1:15]  LOADI     1 -3
  0004  [1:1]   MUL       0 0 1
  ...
constants:
  0  int 70000
```

| Column | Meaning |
|--------|---------|
| `0000` | instruction index (`pc`) |
| `[1:6]` | `line:column` of the instruction's span |
| `LOADK` | mnemonic (`OpCode::name`) |
| `1 0` | operands in the opcode's format (`A Bx` here) |
| `; 70000` | helpful comment: the constant's value, a jump's target |

The disassembly format is covered by snapshot tests, so changing it shows up
as a reviewed diff (chapter 10).

## 5.6 Where to change things

| Task | Where |
|------|-------|
| add an opcode | a line in `opcodes! { … }` with the next number (the test `opcode_numbering_is_dense` enforces order) → handle in `vm.rs` `execute` → emit in `codegen.rs` |
| add a constant type | `Const` variant → `vm.rs` (`LOADK` arm) → `disasm.rs` (`const_repr`, `const_entry`) → a dedup map in `codegen.rs` |
| annotate an opcode in disassembly | `disasm.rs`, `let comment = match op { … }` |
| change field widths | `Instr` constructors/getters + format table; also update the diagram in `opcode.rs` |

## 5.7 Exercises

1. Encode `ADD 2 0 1` by hand as a hexadecimal number (`ADD` = 4). Check with
   `format!("{:#010x}", Instr::abc(OpCode::ADD, 2, 0, 1).0)` in a test.
2. Why is `LOADI`'s immediate signed but `LOADK`'s index unsigned?
3. `sj_offset` casts to `i32` *before* shifting right. What would go wrong
   with `(self.0 >> 8) as i32` for a negative jump?
